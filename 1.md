可以。针对 IM 消息这种**按房间顺序写入、按时间倒序分页、偶尔按 ID 查询/删除**的场景，Pebble 的性能关键不是模仿 SQL，而是提前设计好访问路径。

Pebble 支持原子 Batch、范围迭代、前缀迭代、反向迭代、Bloom Filter 和 Range Delete；但它没有事务隔离、SQL 查询优化器或自动二级索引，因此每一种查询都需要明确对应的 Key 索引。([GitHub][1])

## 一、推荐的数据布局

不要这样存：

```text
message:{id} -> JSON
```

这样按房间分页需要扫描全库。

推荐：

```text
主消息索引：
m | room_id | inverted_timestamp | message_id
    -> sender_id | content

消息 ID 索引：
i | message_id
    -> room_id | timestamp

发送者索引，可选：
s | sender_id | inverted_timestamp | message_id
    -> room_id

用户房间已读位置：
r | user_id | room_id
    -> timestamp | message_id
```

其中：

```go
invertedTimestamp := ^uint64(timestamp)
```

时间越新，反转后的数字越小，所以用 Pebble 默认的字节升序迭代，就能直接获得：

```text
最新消息
次新消息
更老消息
```

不需要反向迭代，也不需要排序。

# 三、二进制编码

这里完全不调用 `json.Marshal`。

`Content` 本身已经是 JSON 原始字节，只需要原样存入 Value。

```go
package messagestore

import (
	"encoding/binary"
	"encoding/json/jsontext"

	"github.com/google/uuid"
)

const (
	prefixMessage byte = 'm'
	prefixID      byte = 'i'
	prefixSender  byte = 's'
	prefixRead    byte = 'r'
	prefixCount   byte = 'c'
)

const (
	messageKeySize     = 1 + 16 + 8 + 16
	messageValueHeader = 16

	idKeySize   = 1 + 16
	idValueSize = 16 + 8

	senderKeySize   = 1 + 16 + 8 + 16
	senderValueSize = 16

	readKeySize   = 1 + 16 + 16
	readValueSize = 8 + 16
)

func invertedTimestamp(timestamp int64) uint64 {
	return ^uint64(timestamp)
}

func restoreTimestamp(value uint64) int64 {
	return int64(^value)
}

func appendMessageKey(
	dst []byte,
	roomID uuid.UUID,
	createdAt int64,
	messageID uuid.UUID,
) []byte {
	start := len(dst)
	dst = append(dst, make([]byte, messageKeySize)...)

	dst[start] = prefixMessage
	copy(dst[start+1:start+17], roomID[:])

	binary.BigEndian.PutUint64(
		dst[start+17:start+25],
		invertedTimestamp(createdAt),
	)

	copy(dst[start+25:start+41], messageID[:])

	return dst
}

func appendMessagePrefix(dst []byte, roomID uuid.UUID) []byte {
	dst = append(dst, prefixMessage)
	dst = append(dst, roomID[:]...)
	return dst
}

func appendIDKey(dst []byte, messageID uuid.UUID) []byte {
	dst = append(dst, prefixID)
	dst = append(dst, messageID[:]...)
	return dst
}

func appendSenderKey(
	dst []byte,
	senderID uuid.UUID,
	createdAt int64,
	messageID uuid.UUID,
) []byte {
	start := len(dst)
	dst = append(dst, make([]byte, senderKeySize)...)

	dst[start] = prefixSender
	copy(dst[start+1:start+17], senderID[:])

	binary.BigEndian.PutUint64(
		dst[start+17:start+25],
		invertedTimestamp(createdAt),
	)

	copy(dst[start+25:start+41], messageID[:])

	return dst
}

func appendSenderPrefix(dst []byte, senderID uuid.UUID) []byte {
	dst = append(dst, prefixSender)
	dst = append(dst, senderID[:]...)
	return dst
}

func appendReadKey(
	dst []byte,
	userID uuid.UUID,
	roomID uuid.UUID,
) []byte {
	dst = append(dst, prefixRead)
	dst = append(dst, userID[:]...)
	dst = append(dst, roomID[:]...)
	return dst
}

func appendCountKey(dst []byte, roomID uuid.UUID) []byte {
	dst = append(dst, prefixCount)
	dst = append(dst, roomID[:]...)
	return dst
}

func encodeMessageValue(
	dst []byte,
	senderID uuid.UUID,
	content jsontext.Value,
) []byte {
	dst = append(dst, senderID[:]...)
	dst = append(dst, content...)
	return dst
}

func decodeMessage(
	key []byte,
	value []byte,
) (Message, error) {
	if len(key) != messageKeySize || len(value) < messageValueHeader {
		return Message{}, ErrInvalidRecord
	}

	var message Message

	copy(message.RoomID[:], key[1:17])
	message.CreatedAt = restoreTimestamp(
		binary.BigEndian.Uint64(key[17:25]),
	)
	copy(message.ID[:], key[25:41])
	copy(message.SenderID[:], value[:16])

	contentLength := len(value) - 16
	message.Content = make(jsontext.Value, contentLength)
	copy(message.Content, value[16:])

	return message, nil
}
```

补充错误：

```go
var ErrInvalidRecord = errors.New("invalid message record")
```

这里唯一不可避免的复制是：

```go
message.Content = make(...)
copy(...)
```

因为 Pebble `Get` 和 Iterator 返回的 Value 生命周期受到对应 Closer 或 Iterator 限制。不能把底层 Value 直接暴露出去，否则关闭 Iterator 后数据就无效了。

# 四、Pebble 实现

## 打开数据库

```go
package messagestore

import (
	"github.com/cockroachdb/pebble"
	"github.com/cockroachdb/pebble/bloom"
)

type PebbleRepository struct {
	db *pebble.DB

	writeSync   *pebble.WriteOptions
	writeNoSync *pebble.WriteOptions

	batchPool sync.Pool
}

type OpenOptions struct {
	CacheSize    int64
	MemTableSize uint64
	MaxOpenFiles int
}

func Open(
	path string,
	options OpenOptions,
) (*PebbleRepository, error) {
	cacheSize := options.CacheSize
	if cacheSize <= 0 {
		cacheSize = 512 << 20
	}

	memTableSize := options.MemTableSize
	if memTableSize == 0 {
		memTableSize = 64 << 20
	}

	maxOpenFiles := options.MaxOpenFiles
	if maxOpenFiles <= 0 {
		maxOpenFiles = 1000
	}

	cache := pebble.NewCache(cacheSize)

	db, err := pebble.Open(path, &pebble.Options{
		Cache:        cache,
		MemTableSize: memTableSize,
		MaxOpenFiles: maxOpenFiles,

		Levels: []pebble.LevelOptions{
			{
				FilterPolicy: bloom.FilterPolicy(10),
			},
		},

		// 根据部署环境选择是否开启。
		// DisableWAL: false,
	})
	cache.Unref()

	if err != nil {
		return nil, err
	}

	repository := &PebbleRepository{
		db: db,
		writeSync: &pebble.WriteOptions{
			Sync: true,
		},
		writeNoSync: &pebble.WriteOptions{
			Sync: false,
		},
	}

	return repository, nil
}

func (r *PebbleRepository) Close() error {
	return r.db.Close()
}

func (r *PebbleRepository) pebbleWriteOptions(
	options WriteOptions,
) *pebble.WriteOptions {
	if options.Durable {
		return r.writeSync
	}

	return r.writeNoSync
}
```

实际工程中，`Levels` 最好完整初始化所有层，而不是只放一个元素。若你的 Pebble 版本默认会自动填充，可以直接省略 `Levels`，先使用默认配置做基准测试。

# 五、单条写入与批量写入

## 核心写入函数

```go
func putMessageToBatch(
	batch *pebble.Batch,
	message *Message,
) error {
	if message.ID == uuid.Nil {
		return errors.New("message id is empty")
	}

	if message.RoomID == uuid.Nil {
		return errors.New("room id is empty")
	}

	if message.SenderID == uuid.Nil {
		return errors.New("sender id is empty")
	}

	/*
		主消息：

		m|room|time|id -> sender|content
	*/
	messageKeyLength := messageKeySize
	messageValueLength := messageValueHeader + len(message.Content)

	messageOp, err := batch.SetDeferred(
		messageKeyLength,
		messageValueLength,
	)
	if err != nil {
		return err
	}

	messageOp.Key[0] = prefixMessage
	copy(messageOp.Key[1:17], message.RoomID[:])

	binary.BigEndian.PutUint64(
		messageOp.Key[17:25],
		invertedTimestamp(message.CreatedAt),
	)

	copy(messageOp.Key[25:41], message.ID[:])

	copy(messageOp.Value[:16], message.SenderID[:])
	copy(messageOp.Value[16:], message.Content)

	if err := messageOp.Finish(); err != nil {
		return err
	}

	/*
		ID 二级索引：

		i|id -> room|timestamp
	*/
	idOp, err := batch.SetDeferred(idKeySize, idValueSize)
	if err != nil {
		return err
	}

	idOp.Key[0] = prefixID
	copy(idOp.Key[1:17], message.ID[:])

	copy(idOp.Value[:16], message.RoomID[:])
	binary.BigEndian.PutUint64(
		idOp.Value[16:24],
		uint64(message.CreatedAt),
	)

	if err := idOp.Finish(); err != nil {
		return err
	}

	/*
		发送者索引：

		s|sender|time|id -> room
	*/
	senderOp, err := batch.SetDeferred(
		senderKeySize,
		senderValueSize,
	)
	if err != nil {
		return err
	}

	senderOp.Key[0] = prefixSender
	copy(senderOp.Key[1:17], message.SenderID[:])

	binary.BigEndian.PutUint64(
		senderOp.Key[17:25],
		invertedTimestamp(message.CreatedAt),
	)

	copy(senderOp.Key[25:41], message.ID[:])
	copy(senderOp.Value, message.RoomID[:])

	return senderOp.Finish()
}
```

`SetDeferred` 允许调用方直接在 Batch 内部缓冲区中编码 Key 和 Value，减少先构建临时切片、再复制进 Batch 的开销。

## 写入接口

```go
func (r *PebbleRepository) PutMessage(
	ctx context.Context,
	message *Message,
	options WriteOptions,
) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	batch := r.db.NewBatch()
	defer batch.Close()

	if err := putMessageToBatch(batch, message); err != nil {
		return err
	}

	return batch.Commit(r.pebbleWriteOptions(options))
}

func (r *PebbleRepository) PutMessages(
	ctx context.Context,
	messages []Message,
	options WriteOptions,
) error {
	if len(messages) == 0 {
		return nil
	}

	batch := r.db.NewBatch()
	defer batch.Close()

	for index := range messages {
		if index&255 == 0 {
			if err := ctx.Err(); err != nil {
				return err
			}
		}

		if err := putMessageToBatch(
			batch,
			&messages[index],
		); err != nil {
			return err
		}
	}

	return batch.Commit(r.pebbleWriteOptions(options))
}
```

这里必须使用：

```go
db.NewBatch()
```

而不是：

```go
db.NewIndexedBatch()
```

普通 Batch 是写优化的。Indexed Batch 内部还需要维护可查询索引，插入成本和内存消耗都更高；官方文档也建议只有在提交前必须读取 Batch 内容时才使用 Indexed Batch。([Go Packages][2])

# 六、按 ID 查询消息

```go
type messageLocation struct {
	RoomID    uuid.UUID
	CreatedAt int64
}

func (r *PebbleRepository) getMessageLocation(
	messageID uuid.UUID,
) (messageLocation, error) {
	var key [idKeySize]byte

	key[0] = prefixID
	copy(key[1:], messageID[:])

	value, closer, err := r.db.Get(key[:])
	if errors.Is(err, pebble.ErrNotFound) {
		return messageLocation{}, ErrMessageNotFound
	}
	if err != nil {
		return messageLocation{}, err
	}
	defer closer.Close()

	if len(value) != idValueSize {
		return messageLocation{}, ErrInvalidRecord
	}

	var location messageLocation
	copy(location.RoomID[:], value[:16])

	location.CreatedAt = int64(
		binary.BigEndian.Uint64(value[16:24]),
	)

	return location, nil
}

func (r *PebbleRepository) GetMessage(
	ctx context.Context,
	messageID uuid.UUID,
) (Message, error) {
	if err := ctx.Err(); err != nil {
		return Message{}, err
	}

	location, err := r.getMessageLocation(messageID)
	if err != nil {
		return Message{}, err
	}

	var key [messageKeySize]byte

	key[0] = prefixMessage
	copy(key[1:17], location.RoomID[:])

	binary.BigEndian.PutUint64(
		key[17:25],
		invertedTimestamp(location.CreatedAt),
	)

	copy(key[25:41], messageID[:])

	value, closer, err := r.db.Get(key[:])
	if errors.Is(err, pebble.ErrNotFound) {
		return Message{}, ErrMessageNotFound
	}
	if err != nil {
		return Message{}, err
	}
	defer closer.Close()

	return decodeMessage(key[:], value)
}

func (r *PebbleRepository) MessageExists(
	ctx context.Context,
	messageID uuid.UUID,
) (bool, error) {
	if err := ctx.Err(); err != nil {
		return false, err
	}

	var key [idKeySize]byte
	key[0] = prefixID
	copy(key[1:], messageID[:])

	_, closer, err := r.db.Get(key[:])
	if errors.Is(err, pebble.ErrNotFound) {
		return false, nil
	}
	if err != nil {
		return false, err
	}

	if err := closer.Close(); err != nil {
		return false, err
	}

	return true, nil
}
```

按 ID 查询会有两次 Point Get：

1. 根据 ID 获取 RoomID、CreatedAt。
2. 根据完整主键获取消息。

这是为了让房间消息顺序扫描足够快。

如果你的业务大量按 ID 查询，可以增加一份冗余：

```text
i|id -> 完整 Message
```

但消息内容会在磁盘保存两份。多数 IM 系统不值得这样做。

# 七、房间消息游标分页

```go
func prefixUpperBound(prefix []byte) []byte {
	upper := append([]byte(nil), prefix...)

	for index := len(upper) - 1; index >= 0; index-- {
		if upper[index] != 0xff {
			upper[index]++
			return upper[:index+1]
		}
	}

	return nil
}

func normalizeLimit(limit int) int {
	switch {
	case limit <= 0:
		return 50
	case limit > 500:
		return 500
	default:
		return limit
	}
}

func (r *PebbleRepository) ListRoomMessages(
	ctx context.Context,
	roomID uuid.UUID,
	options ListOptions,
) (MessagePage, error) {
	limit := normalizeLimit(options.Limit)

	var prefix [17]byte
	prefix[0] = prefixMessage
	copy(prefix[1:], roomID[:])

	upperBound := prefixUpperBound(prefix[:])

	iter, err := r.db.NewIter(&pebble.IterOptions{
		LowerBound: prefix[:],
		UpperBound: upperBound,
	})
	if err != nil {
		return MessagePage{}, err
	}
	defer iter.Close()

	valid := false

	if options.Before == nil {
		valid = iter.First()
	} else {
		var seekKey [messageKeySize]byte

		seekKey[0] = prefixMessage
		copy(seekKey[1:17], roomID[:])

		binary.BigEndian.PutUint64(
			seekKey[17:25],
			invertedTimestamp(options.Before.CreatedAt),
		)

		copy(seekKey[25:41], options.Before.MessageID[:])

		valid = iter.SeekGE(seekKey[:])

		// 跳过游标本身，返回比它更老的数据。
		if valid && bytes.Equal(iter.Key(), seekKey[:]) {
			valid = iter.Next()
		}
	}

	messages := make([]Message, 0, limit+1)

	for valid && len(messages) < limit+1 {
		if err := ctx.Err(); err != nil {
			return MessagePage{}, err
		}

		message, err := decodeMessage(
			iter.Key(),
			iter.Value(),
		)
		if err != nil {
			return MessagePage{}, err
		}

		messages = append(messages, message)
		valid = iter.Next()
	}

	page := MessagePage{}

	if len(messages) > limit {
		page.HasMore = true
		messages = messages[:limit]
	}

	page.Messages = messages

	if len(messages) > 0 {
		last := messages[len(messages)-1]

		page.NextCursor = &Cursor{
			CreatedAt: last.CreatedAt,
			MessageID: last.ID,
		}
	}

	return page, nil
}
```

这相当于 SQL：

```sql
SELECT *
FROM messages
WHERE room_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

但是 Pebble 里没有：

* SQL 解析。
* 执行计划。
* 排序。
* 行对象反射。
* JSON 解码。

本质上只是一次连续的 LSM 范围扫描。

# 八、根据发送者分页

```go
func (r *PebbleRepository) ListMessagesBySender(
	ctx context.Context,
	senderID uuid.UUID,
	options ListOptions,
) (MessagePage, error) {
	limit := normalizeLimit(options.Limit)

	var prefix [17]byte
	prefix[0] = prefixSender
	copy(prefix[1:], senderID[:])

	iter, err := r.db.NewIter(&pebble.IterOptions{
		LowerBound: prefix[:],
		UpperBound: prefixUpperBound(prefix[:]),
	})
	if err != nil {
		return MessagePage{}, err
	}
	defer iter.Close()

	valid := false

	if options.Before == nil {
		valid = iter.First()
	} else {
		var seekKey [senderKeySize]byte

		seekKey[0] = prefixSender
		copy(seekKey[1:17], senderID[:])

		binary.BigEndian.PutUint64(
			seekKey[17:25],
			invertedTimestamp(options.Before.CreatedAt),
		)

		copy(seekKey[25:41], options.Before.MessageID[:])

		valid = iter.SeekGE(seekKey[:])

		if valid && bytes.Equal(iter.Key(), seekKey[:]) {
			valid = iter.Next()
		}
	}

	messages := make([]Message, 0, limit+1)

	for valid && len(messages) < limit+1 {
		key := iter.Key()
		value := iter.Value()

		if len(key) != senderKeySize ||
			len(value) != senderValueSize {
			return MessagePage{}, ErrInvalidRecord
		}

		createdAt := restoreTimestamp(
			binary.BigEndian.Uint64(key[17:25]),
		)

		var messageID uuid.UUID
		copy(messageID[:], key[25:41])

		var roomID uuid.UUID
		copy(roomID[:], value[:16])

		var messageKey [messageKeySize]byte
		messageKey[0] = prefixMessage
		copy(messageKey[1:17], roomID[:])

		binary.BigEndian.PutUint64(
			messageKey[17:25],
			invertedTimestamp(createdAt),
		)

		copy(messageKey[25:41], messageID[:])

		messageValue, closer, err := r.db.Get(messageKey[:])
		if err != nil {
			if errors.Is(err, pebble.ErrNotFound) {
				valid = iter.Next()
				continue
			}

			return MessagePage{}, err
		}

		message, decodeErr := decodeMessage(
			messageKey[:],
			messageValue,
		)

		closeErr := closer.Close()

		if decodeErr != nil {
			return MessagePage{}, decodeErr
		}
		if closeErr != nil {
			return MessagePage{}, closeErr
		}

		messages = append(messages, message)
		valid = iter.Next()
	}

	page := MessagePage{}

	if len(messages) > limit {
		page.HasMore = true
		messages = messages[:limit]
	}

	page.Messages = messages

	if len(messages) > 0 {
		last := messages[len(messages)-1]

		page.NextCursor = &Cursor{
			CreatedAt: last.CreatedAt,
			MessageID: last.ID,
		}
	}

	return page, nil
}
```

这个接口有 N 次 Point Get。如果发送者查询频繁，可以把完整消息冗余到发送者索引：

```text
s|sender|time|id -> room|content
```

空间换读取性能。

# 九、删除单条消息

删除需要同时清理所有索引，所以必须使用原子 Batch。

```go
func (r *PebbleRepository) DeleteMessage(
	ctx context.Context,
	messageID uuid.UUID,
	options WriteOptions,
) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	message, err := r.GetMessage(ctx, messageID)
	if err != nil {
		return err
	}

	batch := r.db.NewBatch()
	defer batch.Close()

	var messageKey [messageKeySize]byte
	messageKey[0] = prefixMessage
	copy(messageKey[1:17], message.RoomID[:])

	binary.BigEndian.PutUint64(
		messageKey[17:25],
		invertedTimestamp(message.CreatedAt),
	)

	copy(messageKey[25:41], message.ID[:])

	var idKey [idKeySize]byte
	idKey[0] = prefixID
	copy(idKey[1:], message.ID[:])

	var senderKey [senderKeySize]byte
	senderKey[0] = prefixSender
	copy(senderKey[1:17], message.SenderID[:])

	binary.BigEndian.PutUint64(
		senderKey[17:25],
		invertedTimestamp(message.CreatedAt),
	)

	copy(senderKey[25:41], message.ID[:])

	if err := batch.Delete(messageKey[:], nil); err != nil {
		return err
	}

	if err := batch.Delete(idKey[:], nil); err != nil {
		return err
	}

	if err := batch.Delete(senderKey[:], nil); err != nil {
		return err
	}

	return batch.Commit(r.pebbleWriteOptions(options))
}
```

Pebble Batch 提交是原子的；一个 Batch 中的主记录和二级索引要么全部可见，要么全部不可见。开启 `Sync` 时，提交返回前还会保证数据已经同步到持久化介质。([Go Packages][2])

# 十一、删除房间全部消息

主消息可以直接 `DeleteRange`：

```go
func (r *PebbleRepository) DeleteRoomMessages(
	ctx context.Context,
	roomID uuid.UUID,
	options WriteOptions,
) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	var prefix [17]byte
	prefix[0] = prefixMessage
	copy(prefix[1:], roomID[:])

	end := prefixUpperBound(prefix[:])
	if end == nil {
		return errors.New("cannot calculate room range")
	}

	batch := r.db.NewBatch()
	defer batch.Close()

	if err := batch.DeleteRange(
		prefix[:],
		end,
		nil,
	); err != nil {
		return err
	}

	return batch.Commit(r.pebbleWriteOptions(options))
}
```

不过这里有一个重要问题：

```text
DeleteRange 只删除 m|room|... 主记录
```

不会自动删除：

```text
i|message_id
s|sender_id|...
```

因此生产实现建议使用两阶段：

1. 迭代该房间消息，批量删除 ID 索引、Sender 索引。
2. 对房间主消息执行 `DeleteRange`。

或者对整个房间使用逻辑删除：

```text
d|room_id -> deleted_at
```

查询时先判断房间是否删除，再由后台异步清理索引。大房间删除几百万消息时，这种方式更稳。

# 十二、已读游标

```go
func (r *PebbleRepository) SetReadCursor(
	ctx context.Context,
	userID uuid.UUID,
	roomID uuid.UUID,
	cursor Cursor,
	options WriteOptions,
) error {
	if err := ctx.Err(); err != nil {
		return err
	}

	var key [readKeySize]byte
	key[0] = prefixRead
	copy(key[1:17], userID[:])
	copy(key[17:33], roomID[:])

	var value [readValueSize]byte

	binary.BigEndian.PutUint64(
		value[:8],
		uint64(cursor.CreatedAt),
	)

	copy(value[8:24], cursor.MessageID[:])

	return r.db.Set(
		key[:],
		value[:],
		r.pebbleWriteOptions(options),
	)
}

func (r *PebbleRepository) GetReadCursor(
	ctx context.Context,
	userID uuid.UUID,
	roomID uuid.UUID,
) (Cursor, error) {
	if err := ctx.Err(); err != nil {
		return Cursor{}, err
	}

	var key [readKeySize]byte
	key[0] = prefixRead
	copy(key[1:17], userID[:])
	copy(key[17:33], roomID[:])

	value, closer, err := r.db.Get(key[:])
	if errors.Is(err, pebble.ErrNotFound) {
		return Cursor{}, ErrMessageNotFound
	}
	if err != nil {
		return Cursor{}, err
	}
	defer closer.Close()

	if len(value) != readValueSize {
		return Cursor{}, ErrInvalidRecord
	}

	cursor := Cursor{
		CreatedAt: int64(
			binary.BigEndian.Uint64(value[:8]),
		),
	}

	copy(cursor.MessageID[:], value[8:24])

	return cursor, nil
}
```

# 十三、房间消息数量

## 方案一：扫描统计

```go
func (r *PebbleRepository) CountRoomMessages(
	ctx context.Context,
	roomID uuid.UUID,
) (uint64, error) {
	var prefix [17]byte
	prefix[0] = prefixMessage
	copy(prefix[1:], roomID[:])

	iter, err := r.db.NewIter(&pebble.IterOptions{
		LowerBound: prefix[:],
		UpperBound: prefixUpperBound(prefix[:]),
	})
	if err != nil {
		return 0, err
	}
	defer iter.Close()

	var count uint64

	for valid := iter.First(); valid; valid = iter.Next() {
		count++

		if count&4095 == 0 {
			if err := ctx.Err(); err != nil {
				return 0, err
			}
		}
	}

	return count, iter.Error()
}
```

这个相当于：

```sql
SELECT COUNT(*) FROM messages WHERE room_id = ?;
```

但它是 O(N)。

## 方案二：维护计数器

高性能实现应维护：

```text
c|room_id -> uint64 count
```

但是多个 goroutine 并发执行“读取旧值、加一、写回”会丢更新。Pebble 本身不提供传统数据库事务，因此有三个选择：

1. 每个 Room 写入固定分片，由单个 writer goroutine 串行维护计数。
2. 使用 Pebble Merge Operator 实现原子增量。
3. 不维护精确计数，使用分片计数器：

```text
c|room_id|shard -> count
```

查询时把 16 或 64 个 shard 相加。

IM 系统通常不应频繁做精确历史消息总数统计，因此我更建议不在热路径维护它。

# 十四、比 Repo 接口更重要的写入优化

你前面的 Benchmark 里 Pebble 1 万条大约 11ms，而 PGX 大约 53ms，Pebble 已经明显更快。剩下的大头如果是 JSON，最有效的优化不是换 JSON 库，而是**不序列化整个 Message**。

你的 Message：

```go
type Message struct {
	ID        uuid.UUID
	RoomID    uuid.UUID
	SenderID  uuid.UUID
	Content   jsontext.Value
	CreatedAt int64
}
```

固定字段总大小：

```text
ID         16 bytes
RoomID     16 bytes
SenderID   16 bytes
CreatedAt   8 bytes
```

没有必要转成：

```json
{
  "id": "...",
  "room_id": "...",
  "sender_id": "...",
  "content": {},
  "timestamp": 123
}
```

那会引入：

* UUID 转字符串。
* 字段名称。
* 数字转文本。
* 字符转义检查。
* 大量临时内存。
* GC 压力。

采用上述布局后：

```text
Key:
1 + 16 + 8 + 16 = 41 bytes

Value:
16 + len(content)
```

`RoomID`、`CreatedAt`、`MessageID` 已经在 Key 中，不再重复写入 Value。

# 十五、生产环境建议增加 Group Commit

真正高吞吐时，不要每条消息：

```go
PutMessage(... Durable: true)
```

因为每条消息都会单独等待磁盘同步。

可以增加一个写入器：

```go
type WriteRequest struct {
	Message Message
	Result  chan error
}

type GroupWriter struct {
	repository *PebbleRepository

	requests chan WriteRequest
	stop     chan struct{}
	done     chan struct{}

	maxBatchSize int
	flushEvery   time.Duration
}
```

核心循环：

```go
func (w *GroupWriter) run() {
	defer close(w.done)

	timer := time.NewTimer(w.flushEvery)
	defer timer.Stop()

	pending := make([]WriteRequest, 0, w.maxBatchSize)

	flush := func() {
		if len(pending) == 0 {
			return
		}

		messages := make([]Message, len(pending))
		for index := range pending {
			messages[index] = pending[index].Message
		}

		err := w.repository.PutMessages(
			context.Background(),
			messages,
			WriteOptions{
				Durable: true,
			},
		)

		for index := range pending {
			pending[index].Result <- err
			close(pending[index].Result)
		}

		pending = pending[:0]
	}

	for {
		select {
		case request := <-w.requests:
			pending = append(pending, request)

			if len(pending) >= w.maxBatchSize {
				flush()

				if !timer.Stop() {
					select {
					case <-timer.C:
					default:
					}
				}

				timer.Reset(w.flushEvery)
			}

		case <-timer.C:
			flush()
			timer.Reset(w.flushEvery)

		case <-w.stop:
			flush()
			return
		}
	}
}
```

例如：

```go
maxBatchSize = 512
flushEvery   = 1 * time.Millisecond
```

这样 512 条消息可以共享一次 WAL Sync。

这通常比纠结 `json.Marshal` 快几个百分点更有效，尤其是 NVMe 上高并发写入时。

# 十六、推荐保留的 Repo 接口

最终建议保留这些，够覆盖绝大多数 IM SQL Repo：

```go
type Repository interface {
	// 写
	PutMessage(ctx context.Context, msg *Message, opts WriteOptions) error
	PutMessages(ctx context.Context, msgs []Message, opts WriteOptions) error

	// 主键查询
	GetMessage(ctx context.Context, id uuid.UUID) (Message, error)
	MessageExists(ctx context.Context, id uuid.UUID) (bool, error)

	// 会话查询
	ListRoomMessages(
		ctx context.Context,
		roomID uuid.UUID,
		opts ListOptions,
	) (MessagePage, error)

	// 用户发送历史
	ListMessagesBySender(
		ctx context.Context,
		senderID uuid.UUID,
		opts ListOptions,
	) (MessagePage, error)

	// 删除
	DeleteMessage(ctx context.Context, id uuid.UUID, opts WriteOptions) error
	DeleteMessages(ctx context.Context, ids []uuid.UUID, opts WriteOptions) error
	DeleteRoomMessages(ctx context.Context, roomID uuid.UUID, opts WriteOptions) error

	// 已读状态
	SetReadCursor(
		ctx context.Context,
		userID uuid.UUID,
		roomID uuid.UUID,
		cursor Cursor,
		opts WriteOptions,
	) error

	GetReadCursor(
		ctx context.Context,
		userID uuid.UUID,
		roomID uuid.UUID,
	) (Cursor, error)

	Close() error
}
```

## 不建议直接实现的 SQL 风格接口

这些在 Pebble 上代价比较大：

```go
SearchContent(keyword string)
ListMessagesByTimeRangeWithoutRoom(...)
CountMessagesByArbitraryConditions(...)
UpdateWhere(...)
DeleteWhere(...)
```

因为它们缺少天然有序索引，最终会退化成全库扫描。

最适合 Pebble 的 IM 查询模式是：

```text
已知 room_id，查询一段连续消息
已知 message_id，查询单条消息
已知 user_id + room_id，查询已读位置
按确定索引字段做范围查询
```

这套设计的写放大大约是每条消息三次逻辑写入：

```text
主消息记录
ID 索引
Sender 索引
```

如果不需要“按发送者查询消息”，直接删除 Sender 索引，写入吞吐和磁盘占用还会进一步改善。对于纯聊天消息系统，我会优先只保留：

```text
m|room|time|id
i|id
r|user|room
```

这是性能、功能和存储空间之间比较舒服的甜点位。
